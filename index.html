Use the AUR on Manjaro without breaking your system

Six short bash scripts that wrap pacman and yay and close the three failures behind almost every Manjaro AUR disaster: the partial upgrade caused by Manjaro's lag behind Arch, the stale-soname breakage after Manjaro catches up, and the unpinned source that builds something other than what you reviewed. No daemon. 271 tests, 118 of them real pacman transactions, plus an integration suite run on a real Manjaro install.

The gap nobody supports

The AUR assumes you are current with Arch. Manjaro's Stable branch deliberately trails Arch by roughly two weeks. Manjaro's own forum says the AUR is used "at your own risk and your own responsibility". That's fair, but knowing the risk is yours only helps if you can see it.

New in 2.0.0

2.0.0 is the result of a full adversarial audit by Claude Opus 5.5 at maximum effort ("Opus Max"). It found 63 defects, 3 of them critical and 18 high, every one reproduced with the real tools, and it fixed them. The method, the findings in CVE form and what is still open are in AUDIT.md.

  • The gate reads a source the way makepkg does. A pin hidden behind a query, or a # in the filename, used to pass and build a moving ref.
  • The AUR's own index decides what a name is. cgit keeps the branches of deleted packages, so a split package could be judged on a dead one.
  • The PKGBUILD has to match its .SRCINFO: every URL, checksum and signing key, compared without running anything. Over 699 real AUR packages it found 6 real disagreements and no false alarms.
  • safeup dry-runs the whole upgrade, so one foreign package that cannot be satisfied no longer stops everything else.
  • "Needs rebuild" is advice that can work. The scan asks yes or no on the spot, tells a package with no source how to go, and stops flagging what a rebuild cannot change.
  • The aliases install themselves, if you say so, for bash, zsh, fish, ksh, tcsh and nushell.

105 of the 271 tests fail against 1.8.0. Release notes.

Quick start

git clone https://github.com/doug445/Satyrus-manjaro.git
cd Satyrus-manjaro
./deploy.sh
safeup                 # pacman -Syu, with the partial-upgrade guard
safeup --check         # what it would do: no root, nothing changed
safeup --aur           # repo upgrade, then AUR updates, then the rebuild scan
aurinstall <pkg>       # yay -S behind the pin-check gate, built in a chroot when possible
aurupdate              # yay -Sua behind the pin-check gate
aur-rebuild-check      # what broke after a library or python bump; offers the rebuild

deploy.sh asks before installing any missing dependency, offers the short aliases (pupdate, yinstall, yupdate) for bash, zsh, fish, ksh, tcsh and nushell, and is idempotent: anything it replaces is backed up first, and a name you already use stays yours.

The protection is in the wrappers, and only there. pacman -Syu, yay -S and Pamac still work after you install this, and none of them goes through any of these checks. Nothing here hooks or replaces the real package managers, on purpose, so the suite protects exactly the commands you run through it. Use the aliases, and keep a bare yay -S for a deliberate override.

"But this automates pacman --ignore"

It does, and that deserves a real answer. --ignore suppresses an upgrade, not dependency resolution. pacman still resolves the whole transaction and refuses one that would leave a dependency unsatisfied, changing nothing. The project tests that against real pacman on every push rather than asserting it, because the whole safety argument rests on it. The partial-upgrade guide shows the transcript. And it only ever holds a foreign package: when a Manjaro library's upgrade breaks an AUR package, the library goes ahead and the AUR package is rebuilt.

Builds against the libraries you actually run

aurinstall builds in Manjaro's own manjaro-chrootbuild by default. linux-aarhus of the Manjaro team suggested it. The chroot is synced to your Manjaro branch, so the package links against the libraries you run rather than whatever the AUR assumed. That fixes stale-soname breakage at build time. AUR dependency chains are built dependencies first, every link is pin-checked in the clone that is about to build, and on a terminal you can read the PKGBUILDs before anything runs.

What it does not do

  • It doesn't enforce anything. Running pacman, yay or Pamac directly bypasses every check; that is deliberate and documented.
  • It doesn't make Manjaro track Arch. If you want Arch's timing, run Arch, or EndeavourOS.
  • It doesn't audit what a PKGBUILD does. Pinning proves you build the commit you reviewed, not that the commit is benign. A PKGBUILD is code; read it.
  • A chroot is build isolation, not a security boundary.
  • It doesn't replace backups or snapshots.

FAQ

Why does the AUR break things on Manjaro?

The AUR assumes you are current with Arch, and Manjaro's Stable branch deliberately trails Arch. Packages built against Arch's newer libraries can need dependencies Manjaro does not have yet, and when Manjaro catches up, AUR packages you built against the older library stop resolving it.

Doesn't automating pacman --ignore cause partial upgrades?

No. --ignore suppresses an upgrade, not dependency resolution: pacman still resolves the whole transaction and refuses one that would leave a dependency unsatisfied. The project's test suite proves this against real pacman transactions on every push.

Does it work on Arch Linux?

It is scoped to Manjaro on purpose. The problem it solves is created by Manjaro's Stable branch trailing Arch; on Arch itself there is no lag to guard against, and none on EndeavourOS, which uses Arch's repositories directly. If you have not installed yet, install EndeavourOS and skip the problem.

Does it make the AUR safe?

No. Pinning proves you build the commit you reviewed, not that the commit is benign, and a chroot is build isolation, not a security boundary. The pin check also reads the PKGBUILD and refuses one whose .SRCINFO hides a source, but a PKGBUILD is code: read it. yay's diff menu stays on for that. The AUR is not supported by Arch or Manjaro.

Has it been audited?

Yes. Version 2.0.0 is the result of a full adversarial audit by Claude Opus 5.5 at maximum effort ("Opus Max"), which found and fixed 63 defects. Each finding was reproduced with the real tools, and the audit is published, with findings in CVE form and what is still open, in AUDIT.md.

Does it stop me running pacman or yay directly?

No. The checks live in the wrappers (safeup, aurinstall, aurupdate) and run only when you use them. pacman -Syu, yay -S and Pamac still work, and they bypass every check. That is deliberate: a gate you can step around on purpose is one you leave installed. Alias your usual commands to the wrappers.
